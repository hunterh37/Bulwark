1. System overview

Bulwark has two runtimes that share one detection engine. Bulwark Cloud is a hosted service on Render: landing page, customer portal, account backend, API, job queue and cloud scanner. Bulwark Edge is a single-file runner that utilities install on their own hosts. Both load the same versioned modules, so a finding has the same rule ID, severity and remediation wherever it was produced.

2. Render deployment

All hosted pieces are defined in render.yaml at the repo root and live in one Render project, Bulwark, in the RealityFilter workspace. The web service builds from packages/cloud on every push to main.

Scaling path

The job queue is a Postgres table claimed with FOR UPDATE SKIP LOCKED, so the same code runs as the inline loop today and as N background workers later without changes. Moving from the inline worker to a dedicated Render worker is a render.yaml change plus INLINE_WORKER=false.

3. Accounts and the customer portal

Signup creates an organization and its first user in one request. Passwords are hashed with scrypt (16-byte salt, 32-byte key). Sessions are random 192-bit tokens; only their SHA-256 hash is stored, with a 30-day expiry. The browser holds the token in an HttpOnly; SameSite=Lax; Secure cookie, and API clients can send it as a bearer token. Every state change writes an audit_log row, shown in the portal.

4. GitHub connection

Two paths reach the same stored credential. With a GitHub OAuth App configured, Connect with GitHub runs the OAuth web flow with a state cookie and repo read:user scope. Without one, the user pastes a fine-grained personal access token limited to Contents: read and Metadata: read on chosen repos. Bulwark validates the token against GET /user before saving it, then seals it with AES-256-GCM. Public repositories scan with no credential.

A cloud scan resolves the ref to a commit SHA, reads the recursive tree, selects up to 400 source and config files under 200 KB (skipping vendor, node_modules, build output), fetches them in batches of 16, runs the org's modules, and stores findings tied to the scan and commit. Files are held in memory for the scan only and never written to disk or the database.

5. Modules

A module is a versioned detector pack: an ID, version, sectors and a list of rules, each with a pattern, severity, message, remediation and a grid-impact flag. Orgs choose which modules run. Edge runners fetch the org's module list on each heartbeat, so a change in the portal reaches every runner on the next cycle.

6. Bulwark Edge: running inside a utility network

Water and power operators usually cannot send SCADA, HMI or PLC tooling source to a SaaS. Bulwark Edge is built for that constraint. The runner is one ES module file (about 11 KB) with no npm dependencies, runnable on any host with Node 20 or later. It walks local Git checkouts, runs modules, writes JSON and SARIF, and, only in connected mode, posts findings (rule, file, line, severity, message) to Bulwark Cloud. Source code never leaves the host in either mode.

8. Fix pipeline

Each finding with a safe rewrite has a Fix button. The portal first requests a dry run: Bulwark reads the file, applies the rule's autofix to the flagged line (adding an import when the rewrite needs one), and rescans the patched file with the org's modules. The patch is accepted only when the rule no longer fires and no other rule fires more than before. The user sees the diff and confirms.

The fix job then reads the file from the default branch head (so a PR never reverts newer commits), repeats the verification, creates bulwark/<rule>-<id>, commits the file through the contents API, and opens a pull request whose body holds the finding, remediation, diff and verification counts. The customer's own CI runs on the branch. Rules without a deterministic rewrite fall back to a Claude patch when ANTHROPIC_API_KEY is set, subject to the same rescan gate; otherwise the button is hidden.

10. Testing and eval

Unit tests (npm test) run the modules against examples/vulnerable-plant, an intentionally vulnerable pump station and EV charger fixture. The end-to-end suite (node test/e2e.mjs <url>) runs against the live deployment: health, pages and downloads, signup, duplicate and bad-password rejection, login, profile update, module selection, invalid GitHub token rejection, repo add, a cloud scan of this repository with expected Modbus, OCPP and AWS-key findings, finding triage, runner token creation, Edge kit download and checksum, an air-gapped scan producing SARIF, a connected scan whose findings appear in the portal, bad runner token and unsigned webhook rejection, and logout. With E2E_GITHUB_TOKEN set it also connects GitHub, scans the private fixture repo hunterh37/bulwark-e2e-plant, checks OSV advisories, opens a real fix pull request, reads the patched file back from the PR branch, then closes the PR and deletes the branch.

The eval (npm run eval) scores the detectors on a labeled corpus of 47 lines (positives and safe look-alikes per rule), 11 autofix cases and 4 lockfiles against live OSV. It writes eval/REPORT.md and fails CI below 0.9 precision or recall, on any missed autofix, or on any dependency mismatch. Current result: precision 1.000, recall 1.000, autofix 10/10, dependencies 4/4. The corpus was written alongside the rules, so these numbers measure regressions, not real-world accuracy; a corpus drawn from public SCADA and OCPP repositories is the next step.

Operational limits

Auth endpoints allow 20 POSTs per IP per 15 minutes; the API allows 600 requests per IP per minute. Unauthenticated GitHub reads are limited to 60 per hour per Render IP; setting GITHUB_TOKEN on the service raises public-repo scans to 5,000 per hour.
