Bulwark Edge

Air-gapped, vendor-agnostic deployment for power stations and grid operators. Draft, Nov 15 2026.

1. Goal

Run the full Bulwark loop (detect, explain, fix, verify) inside a utility network with no internet connection. A small local language model replaces the cloud LLM. Nothing leaves the site except what the operator exports on purpose. The same software runs on Render (hosted), in a customer cloud, and on the Edge appliance.

Rule: Bulwark never sends packets to L0 to L2 devices and never changes controller logic. It reads mirrored traffic and it opens merge requests on internal source repositories. Humans approve every change.

3. Two workloads

A. Code security (software the utility writes or buys with source)

SCADA integrations, historian connectors, DER and EV-charging backends, scripts, IaC. Runner pulls from the internal Git server (GitLab self-managed, Gitea, Bitbucket DC, Azure DevOps Server), scans, asks the local model for a patch, runs tests in a sandbox against an offline package mirror, and opens a merge request.

B. Network detection (OT traffic)

Passive sensor on a SPAN port or hardware TAP. Protocol parsers produce events; small specialised models flag anomalies; the local LLM explains each alert in plain language and maps it to MITRE ATT&CK for ICS. The LLM is a triage and explanation layer. It does not make the detection decision alone.

6. Local model

  • Size: 7B to 14B parameter open-weight code model, 4-bit or 8-bit quantized. Pick per release from current open-weight code models with licenses that allow commercial on-prem use; evaluate on the Bulwark fix benchmark before shipping.
  • Tasks: finding triage, alert explanation, patch generation for small diffs. Large refactors are out of scope.
  • Guardrails: repo content passed as data, no tool access for the model, output must be a unified diff that applies cleanly, then rescan and tests decide. A wrong patch fails closed and never becomes a merge request.
  • Fine-tuning: LoRA adapters trained at Bulwark on synthetic and public vulnerable code (OT protocol handlers, Modbus/DNP3/OCPP/IEC 61850 libraries). Adapters ship in the update bundle.
  • No telemetry from the model server. Prompts and outputs logged locally to the audit log only.

8. Updates without internet

  • Bulwark publishes a monthly bundle (plus emergency bundles for critical CVEs): images, rule packs, OSV/NVD vulnerability DB snapshot, Suricata/Zeek signatures, model weights and adapters, SBOM, release notes.
  • Signed with cosign and an offline root key; the appliance verifies signatures and SHA-256 before import.
  • Transfer: scanned removable media through the site's existing transient cyber asset process, or a one-way data diode inbound.
  • Rollback: previous bundle kept on disk; one command reverts.

9. Security of the appliance itself

  • Measured boot (TPM 2.0), full disk encryption (LUKS, TPM-sealed), read-only root filesystem.
  • No inbound management except local console and the portal on a management VLAN with SSO/LDAP or local MFA.
  • Egress: none by default. Optional one-way diode export of reports to IT or to Bulwark Cloud on Render.
  • Append-only audit log, exportable for NERC CIP-007 (patch and security event evidence) and CIP-010 (configuration baselines).
  • Our own supply chain: SBOM per image, SLSA provenance, reproducible builds, published vulnerability scan of every release.

11. Build order

  1. Docker compose bundle: cloud API, worker, Postgres, llama.cpp server, model-gateway. Runs on one laptop offline.
  2. Gitea adapter + offline OSV DB + rule detector + local-LLM patch flow. Demo: air-gapped fix MR.
  3. Signed bundle tooling and import command.
  4. Zeek + ICSNPP sensor and first anomaly model on Modbus/DNP3 captures (public ICS PCAP datasets for training).
  5. RKE2 + Helm packaging, STIG image, hardware reference SKU, pilot with one utility.

12. Open questions
